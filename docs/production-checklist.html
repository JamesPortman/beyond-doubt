Clues — production readiness

What's left before this can go live

Everything that could be closed from inside the codebase now is closed, including the Postgres store, which is written and passing the entire server test suite against a real database. What remains is mostly accounts, DNS and one legal document — things that need you, not more code.

Closed this session

Was on the blocking list an hour ago. Is not any more.

✓ Postgres store, written and proven done

Storage is now an interface with two implementations. npm run test:pg runs all 20 server tests against a real Postgres instance and they pass — same semantics, same results, same anti-cheat guarantees. Coercion at the boundary handles the trap where Postgres returns BIGINT and COUNT() as strings, which would otherwise have turned "1 + 1 days completed" into "11".

✓ CORS locked down done

The API is bearer-token authenticated, and it was answering Access-Control-Allow-Origin: *. Any page could have spent a signed-in user's session. Now an allowlist, with a test proving an unlisted origin gets no grant at all.

✓ Login codes stop leaking in production done

authRequest returned the six-digit code in the response body — correct for development, an account-takeover hole in production. There is now a sendEmail hook; with NODE_ENV=production the code goes to the hook and the response carries nothing. Tested both ways.

✓ Refuses to boot misconfigured done

In production the server exits rather than starting without DATABASE_URL and ALLOWED_ORIGINS. The failure mode this prevents is the quiet one: booting on SQLite in /tmp, appearing to work, and losing every account on the next deploy.

✓ Health, shutdown, security headers, git done

/api/health checks the database and the board generator, not just that the process is up. SIGTERM drains in-flight requests so nobody loses the move they just made. nosniff, DENY framing, no-referrer. The repo is initialised with a first commit and a .gitignore.

Blocking — nothing ships until these are done

Roughly a day's work in total, and most of it is filling in forms.

1 · Choose where it runs you10 min

Fly.io or Railway with a volume needs zero code changes — npm run serve is the deployment, and SQLite on a mounted disk will carry a daily puzzle game a very long way. Vercel is also ready now that Postgres exists: vercel.json and api/index.ts are written. My recommendation is Fly, and to reach for Postgres when you actually need it rather than on day one.

2 · Provision the database you20 min

Only if you go serverless. Neon or Supabase, then set DATABASE_URL. Put a connection pooler in front — serverless spawns many instances and a hosted Postgres has a connection ceiling. The code opens at most two connections per instance for this reason.

3 · Wire an email provider you1 hr

Resend, Postmark or SES. The sendEmail hook is a four-line implementation; the hour is domain verification — SPF, DKIM and DMARC records. Skip that and your sign-in codes land in spam, which reads to a new player as "this game is broken".

4 · Domain, DNS, TLS you30 min

Every host above issues certificates automatically. Set ALLOWED_ORIGINS to the final domain — including or excluding www deliberately, because a mismatch fails silently in the browser and looks like the API is down.

5 · Set the real launch date you1 min

launchDate is a placeholder of 2026-06-01. The archive walks back to it, so leaving it wrong means the calendar offers boards that never ran — and someone will "complete" a day that predates the game. One line in serve.mjs.

6 · Privacy policy and terms youhalf a day

You store email addresses, which is personal data under PIPEDA and GDPR. You need a privacy policy saying what you keep and why, a terms page, and — this is the part people forget — a working route for account deletion and data export. That is a real requirement, not a nicety, and it is far cheaper to build now than to retrofit around a leaderboard that references user rows.

Before you tell anyone about it

Not blocking a private soft launch. Blocking a public one.

Playwright suite in CI I can do2 hrs

The browser checks currently print output that I read and judge. That is useless as a regression net. Converting them to assertions covers settings persistence, the share-link round trip, the tutorial, offline↔online transition, touch tagging and room concurrency.

Error tracking and backups you1 hr

Sentry or equivalent, plus automated Postgres backups with a restore you have actually tested. An untested backup is a rumour.

Per-IP rate limiting I can do1 hr

Moves are rate limited per play, but sign-in requests are not limited per IP. Someone can currently hammer /api/auth/request and burn your email quota. Cloudflare in front solves it without code.

Mobile layout pass I can do3 hrs

It works on a phone — long-press tagging is implemented — but the layout was designed at desktop width. For a daily puzzle most of your traffic will be a phone at breakfast.

Decide the day boundary youdecision

Everything is UTC right now. At 8pm in Ontario the "daily" has already rolled over. Either document that, or anchor the boundary to a chosen timezone. It is a small change and a large annoyance if you get it wrong after people have streaks.

The honest summary

The software is ready. What stands between you and a live game is one hosting account, one email domain, one DNS record, and one privacy policy. The single thing I would not skip is account deletion, because it is a legal obligation and it is much harder to add later.
